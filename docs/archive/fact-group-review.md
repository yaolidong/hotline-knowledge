# 逐条处理、失败块补录与事实组发布

## 操作流程

在“审核与维护”打开草稿，左侧对照原件，右侧展开“事实组审核”。

1. **逐条处理**：实体和关系均可确认、退回修正或拒绝，填写依据。退回/拒绝不会删除原件或候选，但阻止其所属事实组通过。维护人员可使用“修正此条”修改类型、属性、关系、规则和证据；也可新增遗漏事实或移除有误候选。修正后重新待审，端点仍被引用的实体不能直接移除。
2. **失败块补录**：在“待补录”展开原文，使用表单添加实体、关系及证据。关系可引用此前已抽取的实体。补录必须引用该失败块；所有结果再次经过 Schema 和逐字证据校验。无可抽取事实的块必须明确勾选并说明原因，不能用空提交伪装处理成功。OCR 原文有误时仍应重新解析，不能通过更改引文来规避校验。
3. **事实组审核**：逐块核对全文与本组的关联；其他条款须说明排除依据，包括尚未成功抽取的块。核对条件、否定、例外、材料备选、流程依赖、适用范围和原件，并处理本组质检提示。组内有退回/拒绝条目，或仍依赖失败块时，不能审核通过。
4. **发布此组**：只将该组写入真实图数据库，回读验证成功后加入客服查询范围。页面打开该组图谱。其他组继续待审；原审核草稿仍为 DRAFT，不会因为一个组发布就宣称整份文档发布。

确认条目可以通过整组审核一并完成，不要求逐条重复点击“确认”。单条确认不能替代完整性核对。当前分组依据事项依赖及证据重叠保守生成；共享的不可分证据会合组，暂不提供任意拆组按钮。

## 历史与修订

发布创建独立的不可变版本快照，共享原文件、散列及绝对偏移；图节点和文本块使用该快照的独立 ID。已生成发布快照的草稿冻结内容，仍可继续审核/发布其他既有组；要补录或修改内容，使用“新建修订草稿”，复用已有解析和抽取，不必再次调用模型。

发布失败保留同一个快照供重试，不额外复制节点；中断发布沿用已有恢复机制。已发布快照可通过其详情页“停用”。新修订草稿不会自动停用历史快照，替换有误知识时须明确停用相应旧快照，避免新旧事实同时提供给客服。

退回是要求修正；拒绝是认为当前候选不可采纳；两者均保留处理人、理由、对象和版本记录。不能为使校验通过而删去原文真实存在的限制条件。

## 数据与接口

复用 SQLite 的版本、`parsed_metadata` JSON 和审计表，不新增数据库结构，不清库，不修改 OpenSPG Schema。

- `_fact_review`：逐项判断、组审核、全文覆盖核对、完整性声明及快照关联。对象内容散列决定单条判断是否仍有效；任何内容修正使组审核失效。
- `_manual_baseline`、`_extraction`：保存人工修正和补录；重试其他失败块时作为恢复基线。人工处理不自动批准知识。重试会清除组审核状态，模型新结果仍需重新核对。
- `_group_publication`：快照的原草稿 ID、版本、事实组、审核依据及证据偏移映射。快照只收录审核组的连续证据范围；原文件阅读仍保留全文，全文不因此自动成为已发布事实。
- `fact_review.py` 负责分组、判断、人工补录及快照；原 `GraphStore.publish` 负责 KAG 子图、OpenSPG 写入、Neo4j 回读，原查询服务仍以 PUBLISHED 版本为白名单。

所有写接口要求 `expected_version` 和非空 `note`。角色沿用现有授权：维护人员修正和补录，审核人员确认/退回/拒绝和发布，管理员两者兼有，客服只查询。

| 接口 | 用途 |
|---|---|
| GET `/api/revisions/{rid}/fact-review` | 当前条目、事实组、质检、发布状态与版本 |
| POST `/api/revisions/{rid}/facts/{key}/decision` | action：accept / return / reject |
| PUT `/api/revisions/{rid}/extraction` | 保存修正；READY/PARTIAL/FAILED 的已解析未发布版本均可修正 |
| PUT `/api/revisions/{rid}/chunks/{cid}/manual` | extraction 为本次补录增量；可引用原有实体 ID；no_facts 明确空块处置 |
| POST `/api/revisions/{rid}/groups/{gid}/review` | action：approve / return；approve 要求 checks、coverage、issue_resolutions |
| POST `/api/revisions/{rid}/groups/{gid}/publish` | 生成或重试不可变快照，成功返回快照版本 |
| POST `/api/revisions/{rid}/review-copy` | 复制为修订草稿，保留历史与原件 |

组审核的 `checks` 固定为 conditions/materials/scope/evidence，均须 true。`coverage` 必须覆盖该版本全部块，本组证据块使用 included，其他块使用 unrelated 并附排除依据。当前块集合或版本变化会拒绝旧请求。模型不能替代人工填写这些审核结论。

旧整篇审核 API 为未采用事实组流程的历史调用保留兼容；一旦草稿发生条目判断、补录或组审核，不能再通过旧接口绕过组审核。历史整篇已发布记录不迁移、不修改；新页面对待审草稿默认采用事实组流程。

## 验证与边界

- `tests/test_fact_review.py`：角色、版本、完整性核对、退回阻断、人工补录、原文校验、组隔离、RAG 证据范围、失败重试和修订保护。图使用明确契约替身，不作为真实图联调。
- `tests/test_fact_review_browser.py`：真实临时 HTTP 服务及 Edge 表单，补录实体/关系、逐条退回与修正、完整性校验和发布交互；抽取来自合成标注，图为契约替身。
- `scripts/validate_fact_groups.py`：真实 DeepSeek、浏览器、OpenSPG 和 Neo4j；仅审核其自身的合成资料。2026-11-04 的两组资料仅发布甲组，真实回读 4 节点/4 边，DeepSeek 问答引文仅来自该快照，乙组保持待审。报告位于 `test-results/fact-groups/20261104T093111/`。

自动分组和逐字证据校验不能证明语义完整。审核人员必须识别漏抽条件、跨条引用和例外；证据不足时应退回，不能仅勾选确认。该版本没有自动行政资格裁定、自动证明政策完整性、任意人工拆组或自动替换旧发布快照。
