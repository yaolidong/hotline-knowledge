# 政务热线知识系统：业务深化与同类工具对照

评估日期：2026-11-04。依据：当前应用源码、现有验证记录，以及下文链接的官方文档/项目仓库。本轮是评估与路线建议，仅新增此文档；未安装竞品、未执行性能对比、未修改运行服务、模型配置或知识数据。文中“建议”均为待实施项，不能视为已完成功能。

## 1. 判断

当前系统已经具备真实导入、抽取、审核、OpenSPG 写图、Neo4j 读取、原件定位和证据问答闭环。下一阶段应围绕“客服能快速作答、审核员能修正、政策变化能更新、错误能定位并回归验证”建设，而非仅增加模型、节点类型或图谱动画。

建议保持现有 OpenSPG/KAG 主链和模块化单体，增加业务交互与明确的数据契约。借鉴通用平台的连接器、流水线观察、检索调试、业务图视角和评测能力。暂不整体替换为另一个 RAG 平台；新平台不能直接替代已经实现的政务审核、地区时间约束和版本证据。

## 2. 源码确认的关键差距

| 位置 | 已确认的实现 | 业务影响/待改进 |
|---|---|---|
| `hotline/static/app.js` 的知识修正区 | 仍通过完整 JSON 修改实体、关系和证据；有逐项质检确认 | 非技术维护人员难以修正；勾选提示不等于语义问题已解决 |
| `hotline/static/chat-view.js`、`models.py:Question` | 界面保存本页对话，后端接收当前问题和地区/事项/日期；无会话实体或指代字段 | 已支持部分范围内追问，但不具备完整的多轮指代消解、服务端会话恢复和话题切换管理 |
| `query.py`、`qa.py` | 对合成资料显示警告，检索入口未按 synthetic 排除 | 上线前应建立测试与正式语料的检索隔离，不能只依靠提示文字 |
| `graph.py:build_subgraph` | 实体 ID 含文档版本；所有节点使用文档级 region | 已保留版本，但通用实体、地方实施事项和事实适用范围尚未分别建模 |
| `identity.py` | 同文档地区、同类型候选，确认/撤销保存在 audit | 身份审核尚未参与查询；引用同一国家法律的不同地方指南无法靠当前同地区策略统一身份 |
| `query.py:conflicts` | 同关系在不同来源的名称集合不一致即提示来源差异 | 不能区分同义、补充、不完整抽取、时间差异与真正互斥要求 |
| `query.py:temporal_status` | 保守检查明示施行/失效日期；有效性问句不轻率断定有效 | 尚无条款级修订传播、业务时间/记录时间查询、有效性核查任务 |
| `qa.py:_retrieve`、`embedding.py` | 已发布范围过滤后进行关键词/向量融合；有候选与上下文上限 | 尚无面向管理员的检索诊断页、重排实验与持久化向量索引；不能假设现有缓存扫描适合大规模并发 |
| `workflow.py` | 单进程工作线程，解析后抽取，失败保存状态；重处理创建版本 | 缺少可复用阶段产物、按阶段恢复、业务任务分派和更新影响清单 |
| `parsing.py`、`evidence.py` | PDF/OCR 区域和 DOCX 单元格可定位 | 复杂 PDF 表格、图中分支流程、附件绑定和 VLM 证据提取仍不足 |

以上是功能边界，不能据此推导实际线上错误率。现有 136 项通过的回归记录证明其覆盖的行为，不代表真实政策语义准确率。

## 3. 前端应按角色与业务对象组织

### 客服工作区

保留对话中心，查询范围改为可见、可修改的标签，标注“从问题识别/本会话确认/工作区默认”。工作区默认地区只能作为可撤销提示，不能覆盖问题中明确的外地诉求。只有缺失信息会改变答案时才追问，不要求每次填写地区、日期和事项。

答案分为简短答复、关键条件/例外、办理信息卡、证据和待核实项。现有复制答复、原件定位继续复用。增加“复制接线话术”和“复制工单记录”两个输出模板；前者简洁，后者保留所用版本和证据。两者均不得省略影响适用范围的限制。

会话状态只保存经确认的事项、地区、时间及必要事实；每轮重新检索，模型历史回答不进入可信证据。支持话题切换提示和一键清除范围。恢复历史会话时标识答案形成时的版本，重新回答要检查来源是否已停用。

增加“依据不符、答非所问、缺少材料/例外、政策可能过期”等结构化反馈，并携带本轮检索 trace ID。客服看可理解的状态；解析器、Embedding、Schema JSON 等信息只在维护工具中出现。

### 知识维护与审核工作区

以事项目录和资料目录为入口。事项详情集中展示条件、材料、流程、部门、渠道、时间费用、证据、待审更改和相关文件；不再要求维护人员从多个独立文档中自行拼出事项全貌。

审核工作台采用原件、结构化事实、问题/修改记录联动布局，可收起侧栏并支持键盘切换。常用编辑用表单、实体选择器、关系端点选择器、条件树编辑器；JSON 保留为高级入口。每次修改展示前后差异、关联原文和重新校验结果。

质检问题分为阻断错误和可解释警告。处理方式包括已修正、证据确认、暂不能确认、误报及理由；不能以“全部勾选”替代问题处置。初期继续以文档版本为发布单位，避免过早引入部分发布造成依赖不完整。

### 图谱工作区

在现有拖拽、缩放、布局和属性面板基础上增加业务视角：事项办理、政策沿革、部门职责、原文证据。默认聚焦某个事项及一至两跳邻域，来源块可收起但始终可追踪。不同边样式区分原文事实、身份关联、派生结论；颜色不作为唯一含义载体。

支持保存筛选视图、按日期比较、查看“为什么关联”和受限路径查询。保存的是查询条件和可见视图，不是绕过发布/权限校验的永久数据快照。大图先分页和按需展开，性能测量后再决定是否替换渲染技术。

## 4. 业务流程与知识更新

建议流程：来源登记 → 获取与版本识别 → 解析质量检查 → 抽取及校验 → 身份候选/变更影响 → 人工处置 → 审核发布 → 客服使用 → 问题反馈 → 回归验证。

- 处理状态、知识发布状态、政策业务状态分开保存和展示。任务完成不代表已发布；已发布不代表政策现行有效；来源失效也不等于历史事实可以删除。
- 新文件进入后区分文件修订、系统重跑、政策新版本。文件哈希去重不能识别政策修订；抽取重跑版本不能冒充政策生效版本。
- 做条款及事实差异比较，先解释“新增、删除、改写、仅版面变化、解析差异”，再列出受影响事项、答案模板、条件与缓存。不能按新发布日期自动覆盖旧要求。
- 保存阶段产物与模型/提示词/Schema/解析器版本。解析器版本或文档没变时可复用解析结果；重跑失败阶段仍须经过证据与发布检查。
- 每个事项有责任部门、知识维护责任人、复核记录；复核周期是管理属性，不能由系统捏造为政策有效期限。
- 试用前隔离合成/真实语料；对外使用前补组织登录、文档级权限、备份演练和并发故障测试。权限过滤要同时覆盖图、原文、向量、引用、下载和缓存。

## 5. 输入数据源：增加结构化权威数据，而非仅增加文件格式

优先接入当地政务服务事项实施清单、部门与区划目录，通过已授权 API、CSV/XLSX 导入映射成稳定事项编码、实施主体与服务属性。这比单靠 LLM 从文件猜测事项身份可靠。基本目录与具体实施清单的区分可参考[市场监管总局的标准解读](https://www.samr.gov.cn/bzjss/bzjd/art/2021/art_a0c44a1f85224970b49eb7663defcfd7.html)；该历史解读用于说明建模思路，实际字段和编码版本必须以接入方当前数据契约为准。

其次增加政府站点来源目录与附件采集：登记官方页面、原件 URL、发布单位、抓取时间、文件哈希、授权方式和更新策略。保存每次内容快照，识别正文和附件变化，新增版本进入待审队列。获取失败、页面删除或网页修改不能自动认定政策废止。网页正文转写与原始 PDF 必须区分。

FAQ 和历史工单可用于发现群众口语表达、检索别名和知识缺口；必须脱敏、明确来源可信级别，不能将一次客服答复直接升级为政策事实。正式政策、办事指南、政策解读、业务口径、历史案例应带类型与使用边界。

音频转写可在真实热线集成阶段试点，用于提取本次咨询诉求；不是权威政策输入。视频政策解读暂后置，除非实际业务资料占比足够高。

## 6. 多模态处理：围绕政务难点分流

| 输入难点 | 建议处理 | 必须保留/验证 |
|---|---|---|
| 文字层完整的普通 PDF | 继续原生解析，避免不必要 OCR/VLM | 阅读顺序、条款、页码、原件定位 |
| 模糊或混合文字层扫描件 | 按页质量判定，必要时 OCR；人工更正形成派生文本版本 | 原始图像、原始 OCR、修正记录；更正后重新绑定证据偏移 |
| 复杂材料表 | 结构化表格模型，恢复跨页表头、合并单元格、脚注和条件列 | 材料名、份数、原/复印件、适用情形必须属于正确行列 |
| 办理流程图 | VLM/图形解析提出步骤、箭头与分支标签候选，人工核对 | 图区域、方向、条件、返回/终止路径；不能把空间排列当时间顺序 |
| 附件、申请表、红头信息 | 绑定正文与附件版本，提取明示字段和用途 | 不凭红头、印章或视觉样式认定文件真实或现行有效 |

建立统一的文档证据对象：原件 → 页面 → 区域/表格单元格 → 文字块或视觉对象 → 事实断言。实体可关联多种证据，但“出现在某页”与“该区域支持某事实”是不同关系。

同一 PDF 的文字层、OCR 与 VLM 描述共享同一上游来源，不能当成三份独立佐证。分别记录 OCR 识别分数、关联证据、审核状态；不生成混合各种含义的“政策可信度 98%”。

解析器采用可替换适配器，先用真实中文红头、材料表、跨页表、流程图小样本对比，再选择。可参考 [Docling 的统一文档模型](https://docling-project.github.io/docling/concepts/docling_document/)和 [MinerU 的结构化文档处理](https://github.com/opendatalab/MinerU)。本次未安装或跑两者，不能判断谁在本项目语料上更准确。

## 7. 实体对齐与图谱建模

建议分清三个对象：稳定实体、某文档中的提及、带地区/时间/条件/来源的事实断言。继续保留现有版本实体和证据，在其上逐步增加经审核的规范实体映射，不先物理合并历史节点。

| 对象 | 候选身份依据 | 需要避免 |
|---|---|---|
| 政府部门 | 权威机构标识、行政辖区、层级、机构沿革 | 将更名、合并、承接职责一律当作同一实体 |
| 政务事项 | 基本事项与地方实施事项分层；编码及实施主体 | 将同一基本事项在不同地方的要求合并 |
| 政策文件 | 发布机关、正式文号、版本/文件链及原件 | 同标题即合并；同一法律被不同地区引用却被永久拆开 |
| 材料/条件/流程 | 可共享材料概念，但要求、份数、例外、顺序属于具体断言 | 因名称相同就继承另一事项的要求 |

对齐候选应显示正向理由和冲突理由，支持明确否决记录、候选组与审核历史。相似度只是排序信号，不能替代身份依据；无法确定的保留未关联状态。先保证匹配精度，再扩大召回。

确认映射后，查询可扩展到同一规范实体的授权已发布来源，但每条事实继续按地区、日期、事项实施实例独立筛选。撤销应使映射索引及缓存失效；不得借身份链绕过源文档可见性，也不能未经检查自动传递 A=B、B=C 得出 A=C。

Schema 仍统一配置维护，并补充版本、兼容性与样例验证。只有明确查询需求时才增加证照结果、补贴项目、职责等节点。期限、费用、份数和联系方式通常先使用有证据的属性或事实限定项。

## 8. 检索、知识推理与输出

### 逐级增加能力

1. 字段检索：部门、材料、条件等使用既有类型与关系；费用、法定时限/承诺时限增加明确字段查询，保留单位和计算口径。
2. 受限路径：事项 → 要求 → 条款 → 文件，或事项 → 部门 → 办理渠道。每一跳均检查发布状态、地区时间及证据；路径存在本身不等于结论成立。
3. 政策比较：在同一适用场景中对齐新旧条款，区分补充、替代、措辞变化、部分废止与抽取缺失。将当前“来源集合不同”的提示细分为差异待核对、互补和有证据的冲突。
4. 条件辅助核对：规则明确且经审核后，使用满足/不满足/未知三值表示。未知不能自动转为否；保留输入来源和缺失条件。输出仅为条件核对，不构成资格或行政裁定。

LLM 可以提出类型化查询计划；查询服务校验白名单关系、参数、权限、时间和跳数后执行。优先评估固定 KAG 版本中的已有算子，不把当前尚未接入的 solver 描述成已可用。向用户展示事实路径、适用条件和原文依据，而不是模型内部思考文本。

检索调试台应展示：识别到的意图/地区/事项/日期、候选、被过滤原因、图查询路径、各路召回、重排、最终送入上下文的证据。客服无结果时只看“需确认范围/资料尚未发布/缺少相关资料”等合规提示；维护人员才查看可授权的详细诊断。

Reranker 应先做离线对比；不能让重排或上下文裁剪丢弃图事实的必须证据、例外和表头。大规模检索先考虑同一 Neo4j 的向量/全文索引与有版本的索引任务，再根据压测决定是否新增存储引擎。

答案建议包含：直接答复、适用范围、完整关键条件/例外、可用办理信息、来源文件/条款、业务有效性、知识审核状态和明确待核实项。`无该规定`、`当前未检索到`、`原文未明确`、`抽取未覆盖`必须区分。引用存在性校验不能证明结论被引用支持，增加断言级支持检查与人工抽检。

若逐字流式输出，事实可能在校验前已经呈现。优先流式显示真实检索阶段进度；答案按通过引用校验的完整句子/段落展示，或整体校验后展示。无法从显示端撤回用户已经看到的错误内容。

## 9. 同类工具：已核实能力与可借鉴点

以下对照包括平台、图工具、解析组件和评测工具，定位不同，不是统一排行榜；官方页面声明不等于已在本机运行验证。

| 工具 | 官方资料明确的相关能力 | 对本系统的借鉴与边界 |
|---|---|---|
| Dify | 可视化知识流水线、逐节点 Test Run、变量检查、分块模板 | 借鉴导入模板和阶段产物检查；暂不自建通用拖拽工作流引擎。见[官方介绍](https://dify.ai/blog/introducing-knowledge-pipeline) |
| RAGFlow | 检索测试展示块、相关度、来源与过滤参数，区分未召回和回答问题 | 建立维护端检索实验室，记录应用与测试使用的配置版本。见[官方检索测试文档](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/retrieval_testing.md) |
| FastGPT | 问答数据/多向量映射、混合检索、重排；文档级权限有版本与鉴权条件 | 引入审核 FAQ 的口语召回、检索对比与文档权限。不能把元数据标签当鉴权；文件级权限文档明确属于商业版，且受成员身份调用条件约束。见[检索说明](https://doc.fastgpt.io/zh-CN/guide/dataset/dataset_engine)、[权限说明](https://doc.fastgpt.io/zh-CN/guide/dataset/collection_permission) |
| Neo4j Bloom | 业务 Perspectives、节点/关系/属性可见性、样式与搜索短语 | 借鉴按事项、部门、沿革、证据的视角，不仅复制视觉配色。见[官方文档](https://neo4j.com/docs/bloom-user-guide/current/bloom-perspectives/bloom-perspectives/) |
| Neo4j LLM KG Builder | 文档/块图与实体图、配置 Schema、抽取后清理及多种检索方式 | 借鉴抽取检查与来源关联。官方仍提示更适合长英文文本，对表格图示有限制，不能推断其更适合中文政务。见[官方说明](https://neo4j.com/labs/genai-ecosystem/llm-graph-builder/) |
| Docling / MinerU | 统一结构化文档表示、复杂文档解析；具体输出和资源依版本而变 | 作为局部解析适配器候选，以中文表格/扫描件基准选择，不整体替换知识治理。见前文官方链接 |
| KAG / Microsoft GraphRAG | KAG 的逻辑形式检索推理；GraphRAG 区分实体局部、全局社区等检索 | 办理信息先采用受限局部图查询；全库主题归纳供管理分析，不能代替逐条政策依据。见[KAG](https://github.com/OpenSPG/KAG)、[GraphRAG 查询类型](https://microsoft.github.io/graphrag/query/overview/) |
| LangSmith | 数据集与实验、离线/在线评测、人工评估 | 借鉴“失败问题→人工标注→回归集”流程，实施可保持本地；不要求将政务数据送入云服务。见[官方评测说明](https://docs.langchain.com/langsmith/evaluation) |

## 10. 建议实施顺序与验收

| 批次 | 工作 | 验收重点 | 相对工作量 |
|---|---|---|---|
| 一：业务可用与排错 | 测试/正式隔离；事项工作台；表单式审核；检索诊断；接线/工单输出与问题反馈 | 普通维护人员不写 JSON 完成典型修正；无结果可定位原因；所有客服入口不混入测试知识 | 中 |
| 二：知识准确与更新 | 真实语料标注；结构化事项目录；表格/流程图解析对比；条款差异和影响分析；质量问题处置 | 材料行列与条件完整性有人工基准；新文件可找出受影响事项；历史证据不被覆盖 | 中至高 |
| 三：关联与受限推理 | 规范实体映射参与检索；类型化多跳计划；条款时间及条件三值核对；受约束会话上下文 | 不因对齐跨地区混答；撤销关联立即影响检索；每个派生结论可重放并解释证据 | 高 |
| 四：规模与运营 | 来源同步、组织鉴权、持久索引、并发任务、备份与恢复、质量运营 | 用实际文档规模与并发压测验收，监控发布延迟、处理失败、p50/p95 和质量回归 | 随部署条件确定 |

四个批次不是完全串行：反馈与标注从第一批就开始；文档级权限及组织鉴权必须在相应内部敏感资料/多用户上线前完成，不能机械等到最后。

初始评估集建议 20–30 份有代表性的真实文件和约 100 个经业务人员确认的问题；这是建议规模，不是已有数据。覆盖同名异地、简称、历史日期、材料 OR、条件 NOT、跨页表格、附件、明确修订/废止、缺失信息、口语追问和多条款联合问题。调参与验收集按文档/事项分开，避免同源片段泄漏。

分别记录解析字段正确性、关键条件完整率、实体对齐误合并/漏合并、检索证据召回、引用支持性、越域回答、无依据回答、正确拒答、审核耗时及响应延迟。不能用引用数量、节点数量或模型自评分替代这些指标；LLM 评审须由人工样本校准。回归集不得混入正式客服可见知识。

尚未知：完整文档量、日更新量、接线并发、真实语言分布、内网 GPU、接入权限和业务验收阈值。测量这些条件后再确定索引/队列/服务拆分及工期，不给出无依据的吞吐或成本承诺。

备选路线是通过已有受控检索 API 接入 Dify/FastGPT 做应用入口；只有明确需要跨业务低代码应用、多连接器且能解决身份透传、版本过滤、双重审计和数据同步时才值得试点。若造成重复知识库或审核旁路，应放弃这一替换方案。当前推荐路线不要求迁移已有图或批量重写历史数据。
