# 政务实体三元组建模核查（2026-11-04）

核查对象：已发布版本 `70e2524c3b4f4abdbeb589939ad52593`，食品经营许可证（餐饮）服务指南。检查了已保存抽取结果、Schema、抽取提示、校验和真实 Neo4j 回读。本次只做核查，未更改或重新发布任何知识。

后续已按本核查实施改造并生成新的待审版本；下文保留原已发布版本的核查事实，不代表新草稿结果。改造内容与真实验证见 [语义升级记录](semantic-upgrade.md)。

## 结论

当前数据具有真实的节点—有向关系—节点结构；业务图混合了实体、概念、条件/步骤节点，另外保留来源文档与文本块。不能仅因尾节点是条件就认定它不是知识图谱；但实体边界、名称规范化、对象/属性/规则区分确实不充分。完成真实运行闭环，不等于语义抽取质量已经达标。

Neo4j 使用[属性图模型](https://neo4j.com/docs/getting-started/appendix/graphdb-concepts/)，节点和关系都可有属性；它不要求直接存成 RDF。[RDF 三元组](https://www.w3.org/TR/rdf11-concepts/#section-triples)的宾语也可以是字面量，因此“所有字段必须变成实体节点”不是标准要求。

| 申请、受理、审批（现场核查）、决定、发证五个节点均无 order | 只有事项与步骤的挂接关系，没有明确步骤顺序，不能据图声称已完整表达流程 |
| 节点 → SUPPORTED_BY → 原文块；来源文档 → HAS_CHUNK → 原文块 | 合理的溯源结构，应与业务关系分开理解、展示及统计 |
| ID 包含文档版本，跨文档不合并 | 便于保存来源和历史，但尚未形成统一可复用的跨文档实体层；canonicalKey 不等于已经完成实体消歧 |

完整版本回读为 20 个领域节点、19 条业务关系，加上两个来源节点及来源关系，共 22 节点、40 关系。此前页面按事项筛选的 21 节点、39 关系是不同查询范围，不是相互矛盾的全库计数。

## 形成原因

`extraction.py` 同时要求 name/aliases/attributes 与 evidence 逐字匹配，`schema.py` 执行该约束。它能限制编造，却没有把原文提及、规范名称、展示摘要分开；空格、错字、长句会进入名称。校验检查类型枚举、关系端点与证据位置，尚不能证明事实蕴含、申请对象与条件的语义区分、材料完整性和流程顺序。

当前通用回归重点是权限、状态、来源、存储和查询行为，不是完整的人工标注语义质量基准；不能用测试通过数证明实体/关系抽取准确率。

## 修正方向（未实施迁移）

1. 区分业务实体、普通属性、条件/材料组/步骤节点、来源证据。为原文提及与规范名称建立不同字段，规范化不能改写证据原文。
2. 主体类别优先使用已有 applicants 属性；确有跨事项查询需要时再增加主体概念类型及适用关系。
3. 条件节点保存稳定 ID、展示名称、完整条款、适用对象与明确逻辑；AND/OR/NOT 仅在原文能够支持时抽取，无法判断时标为待核对。
4. 材料名称、形式、数量、备选规则分离；流程顺序只在原文或版式可验证时建立，不能因为列表排列就无条件推断时间顺序。
5. 以同一份指南先建立人工标准实体/属性/关系/规则，再验证新旧抽取结果。涉及类型、字段或关系变化时生成可审查的新 Schema 和版本迁移方案，不覆盖现有已发布图。

本记录描述当前实现的不足及改进目标，不代表上述模型升级已经完成。
